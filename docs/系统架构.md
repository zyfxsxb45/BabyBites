## 1. 系统概述

### 1.1 我们要做什么

一个面向 6-12 月龄婴儿辅食添加的智能辅助工具。家长输入宝宝的月龄、过敏史、已有喂养记录等信息，系统输出阶段判断、食材/商品风险标签和周度辅食计划。

### 1.2 核心原则

| 原则 | 含义 |
|------|------|
| **安全兜底** | 致敏食材拦截、月龄不适龄拦截由规则引擎执行，LLM 不参与安全决策 |
| **可解释** | 每个风险标签和推荐都附带原因，家长能理解而不是黑箱 |
| **渐进增强** | 先用规则跑通核心流程，再逐步引入 LLM 增强灵活性 |

### 2.2 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 知识表示 | JSON + SQLite，**不用知识图谱** | 时间线紧（6月10日demo），JSON+SQLite迭代更快，对安全规则来说确定性更强 |
| 安全控制 | 规则引擎代码硬编码 | 过敏拦截、月龄门槛必须100%准确，不能交给 LLM |
| 参考知识 | Function Calling + 结构化数据查询 | LLM 需要时通过工具调用精确查询，不依赖 prompt 中的碎片知识 |
| LLM 角色 | 语言理解 + 解释生成，**不做决策** | 立项已明确，"大模型不直接决定能不能吃" |

### 3.3 SQLite 表结构（商品/配料部分）

```sql
-- 商品表
CREATE TABLE products (
    id TEXT PRIMARY KEY,
    barcode TEXT,
    brand_id TEXT REFERENCES brands(id),
    name TEXT,
    category TEXT,
    suggested_age_months TEXT,  -- '6+', '8+' 等
    price REAL,
    price_unit TEXT,  -- '元/g'
    source TEXT        -- 'open_food_facts' | 'manual'
);

-- 配料表
CREATE TABLE ingredients (
    id TEXT PRIMARY KEY,
    name TEXT,
    ins_code TEXT,      -- Codex INS 编号
    e_code TEXT,        -- EU E 编号
    category TEXT,      -- '添加剂' | '营养强化剂' | '基础配料'
    is_allergen BOOLEAN DEFAULT 0,
    allergen_id TEXT REFERENCES allergens(id),
    is_added_sugar BOOLEAN DEFAULT 0,
    is_added_salt BOOLEAN DEFAULT 0,
    notes TEXT
);

-- 商品-配料关联表
CREATE TABLE product_ingredients (
    product_id TEXT REFERENCES products(id),
    ingredient_id TEXT REFERENCES ingredients(id),
    sequence INTEGER,   -- 在配料表中的顺序位置
    PRIMARY KEY (product_id, ingredient_id)
);

-- 商品营养成分表
CREATE TABLE product_nutrition (
    product_id TEXT REFERENCES products(id),
    nutrient_name TEXT,
    value_per_100g REAL,
    unit TEXT,
    source TEXT,
    PRIMARY KEY (product_id, nutrient_name)
);
```

## 4. 规则引擎层

### 4.1 规则模块清单

```
rules/
├── __init__.py
├── base.py              # 规则基类和结果类型定义
├── allergen_rules.py    # 过敏拦截
├── age_rules.py         # 月龄适龄判断
├── texture_rules.py     # 质地递进规则
├── interval_rules.py    # 排敏间隔规则（带时序记忆）
├── nutrition_rules.py   # 营养多样性/缺口检查
├── additive_rules.py    # 添加糖/盐/添加剂检测
├── cost_rules.py        # 成本-营养性价比排序
└── rule_engine.py       # 规则调度器：依次执行所有规则，汇总结果
```

### 4.2 规则结果类型

```python
class RuleResult:
    tag: Literal["suitable", "caution", "avoid", "not_applicable"]
    reason: str            # 给家长看的解释
    rule_source: str       # 引用来源（"CDC指南第X条"、"EU 609/2013第Y条"）
    severity: Literal["info", "warning", "error"]

class RuleOutput:
    results: List[RuleResult]
    overall_tag: str       # 综合后的标签
    # 如果任意规则返回 avoid → 整体 avoid
    # 如果任意规则返回 caution 但无 avoid → 整体 caution
    # 全部 suitable → suitable
```

### 4.3 规则函数示例

```python
# age_rules.py

def check_age_appropriateness(food_id: str, age_months: int) -> RuleResult:
    """检查食材是否适龄"""
    food = load_food_data(food_id)
    if age_months < food["min_age_months"]:
        return RuleResult(
            tag="avoid",
            reason=f"{food['name_zh']}建议{food['min_age_months']}月龄后引入，"
                   f"当前宝宝{age_months}月龄尚不适宜",
            rule_source="CDC 固体食物引入指南 / WHO 补充喂养原则",
            severity="error"
        )
    # 检查质地匹配
    stage = get_age_stage(age_months)
    if food["texture_stage"] != stage["texture"]:
        return RuleResult(
            tag="caution",
            reason=f"{food['name_zh']}的质地({food['texture_stage']})"
                   f"与当前阶段({stage['texture']})不完全匹配，需要调整制备方式",
            rule_source="CDC 食物准备指南",
            severity="warning"
        )
    return RuleResult(tag="suitable", ...)
```

### 4.4 规则调度逻辑

```
输入: [候选食材列表, 宝宝画像, 历史记录]

rule_engine.run():
  1. 对每个候选食材依次执行所有规则
  2. 每条规则返回 RuleResult
  3. 汇总: 先合并 tag, 再附带所有 reason
  4. 输出: {食材: [RuleResult...], 整体标签}

输出: 带标签的食材候选列表 → 传给计划生成智能体
```

## 5. 智能体层

### 5.1 用户画像智能体

| 项目 | 内容 |
|------|------|
| **职责** | 从用户输入中提取结构化的宝宝画像 |
| **输入** | 自然语言（"宝宝6个月，对鸡蛋过敏，目前纯母乳喂养..."）|
| **输出** | 结构化 Profile: `{age_months: 6, allergies: ["鸡蛋"], feeding: "breast_milk", ...}` |
| **实现方式** | LLM + 固定字段模板提取 |
| **知识依赖** | 无（纯 NLP）|
| **确定性要求** | 中等（字段可以 LLM 抽取，月龄等关键字段需做格式校验）|

### 5.2 标签解析智能体

| 项目 | 内容 |
|------|------|
| **职责** | 解析用户输入的食材/商品配料表，识别成分和风险 |
| **输入** | 配料文字（"大米、燕麦、苹果粉、柠檬酸(330)、碳酸钙、白砂糖"）|
| **输出** | `[{成分名, 类别, INS编码, 是否致敏物, 是否添加糖, 是否添加剂}]` |
| **实现方式** | LLM 切分配料表 → 查 ingredients 表匹配 → 返回结构化结果 |
| **知识依赖** | ingredients 表（SQLite）中的别名匹配 |
| **确定性要求** | 高（风险成分不能漏标）|

流程细节：
```
配料文字输入
    ↓
LLM 按逗号/括号切分各成分
    ↓
每个成分去 ingredients 表做别名匹配
    ↓
匹配成功 → 返回分类/风险标签
匹配失败（未收录成分）→ LLM 根据名称推断类别，标记为"未验证"
    ↓
汇总输出
```

### 5.3 阶段与安全边界智能体

| 项目 | 内容 |
|------|------|
| **职责** | 判断宝宝是否进入辅食阶段，执行硬性安全拦截 |
| **输入** | 宝宝画像 |
| **输出** | `{can_start: bool, readiness_signals: [...], blocking_reasons: [...]}` |
| **实现方式** | 纯规则引擎，无 LLM 参与 |
| **知识依赖** | age_stages.json, allergen_rules, age_rules |
| **确定性要求** | 100% |

### 5.4 计划生成与优化智能体

| 项目 | 内容 |
|------|------|
| **职责** | 在候选食材中做约束满足 + 多目标排序，生成周度计划 |
| **输入** | 候选食材列表（已打标签的）+ 宝宝画像 |
| **输出** | 周度喂食计划表 |
| **实现方式** | 混合：规则引擎做约束过滤 + LLM 做排序和解释 |
| **知识依赖** | foods.json, nutrients.json, cost_rules |
| **确定性要求** | 约束部分高，排序部分中 |

计划生成流程：
```
候选食材（已过安全筛选）
    ↓
按月龄阶段约束过滤
    ↓
按排敏间隔约束排序（新食材优先安排在前）
    ↓
按营养多样性目标做组合（确保每周覆盖"高铁""高锌""高蛋白"等）
    ↓
按可选约束排序（预算、偏好）→ 可使用 LLM 做灵活排序
    ↓
LLM 生成每日安排 + 自然语言说明
    ↓
输出计划 → 传给校验智能体
```

### 5.5 校验智能体

| 项目 | 内容 |
|------|------|
| **职责** | 二次验证生成的计划是否违反所有硬约束 |
| **输入** | 周计划 + 宝宝画像 |
| **输出** | `{passed: bool, violations: [{day, food, rule, severity}]}` |
| **实现方式** | 纯规则引擎，重新执行所有规则 |
| **知识依赖** | 全部规则模块 |
| **确定性要求** | 100% |

关键设计：这是一个**安全冗余**——计划生成智能体可能因为 LLM 参与而出错，校验智能体作为最后防线重新检查所有硬规则。对标立项文档中的"关键安全判断由规则库和校验模块完成"。

### 5.6 对话记忆与解释智能体

| 项目 | 内容 |
|------|------|
| **职责** | 记录用户反馈、生成可读解释、管理对话上下文 |
| **输入** | 计划/标签 + 规则输出 + 用户反馈 |
| **输出** | 自然语言回应 |
| **实现方式** | 纯 LLM，接收结构化输入生成语言 |
| **知识依赖** | 无（接收规则引擎的结构化输出，转为语言）|
| **确定性要求** | 低（语言表达灵活性正好是 LLM 的优势）|

### 5.7 Chat 智能问答

| 项目 | 内容 |
|------|------|
| **职责** | 回答用户关于婴儿辅食、过敏、营养、喂养技巧等自由提问 |
| **输入** | 自然语言问题（"宝宝便秘怎么办""鳕鱼和带鱼哪个更适合6月龄"）|
| **输出** | 基于知识库的自然语言回答，必要时引用来源 |
| **实现方式** | 知识库检索 + LLM 生成，可选 RAG 增强 |
| **知识依赖** | 全部 JSON 知识库 + SQLite 商品数据 + 标准/指南文档（RAG）|
| **确定性要求** | 中低（需标注"仅供参考"，医疗建议须引导咨询医生）|

Chat 系统与工作流智能体的定位差异：
- 工作流智能体：按固定流程执行（画像→安全→计划→校验），输出是结构化的喂养计划
- Chat 智能问答：自由对话，不限话题，输出是自然语言回答
- Chat 可以利用工作流智能体的能力（如"帮我看看这个配料表"→ 调用标签解析智能体）

回答时遵循的安全边界：
- 引用知识库中的标准/指南作为依据
- 绝不给出医疗诊断建议，始终引导咨询医生
- 对于知识库未覆盖的问题，诚实告知"我目前没有这方面的资料"而非编造

## 7. 数据流全景

### 7.1 一次完整请求的流程

```
[用户] 输入宝宝信息和需求
    │
    ▼
[交互层] 收集结构化输入
    │
    ▼
[用户画像智能体] 提取/校验宝宝画像
    │
    ▼
[阶段与安全边界智能体]
    │  规则引擎: age_rules → 是否可开始辅食
    │  规则引擎: allergen_rules → 已知过敏原拦截
    │
    ├── ❌ 条件不满足 → [解释智能体] → 告知用户原因，结束
    │
    └── ✅ 条件满足
         │
         ▼
[标签解析智能体]（如果有配料输入）
    │  LLM 切分 → ingredients 表匹配 → 输出风险标签
    │
    ▼
[规则引擎] 对全食材库执行一次筛选
    │  age_rules + allergen_rules + texture_rules
    │  → 输出候选食材池（带规则结果）
    │
    ▼
[计划生成与优化智能体]
    │  约束满足 → 多目标排序 → LLM 生成每日安排
    │
    ▼
[校验智能体]
    │  规则引擎再次验证全计划
    │
    ├── ❌ 校验不通过 → 回退到计划生成步骤，加入新约束
    │
    └── ✅ 校验通过
         │
         ▼
[解释智能体] 生成自然语言说明
    │
    ▼
[交互层] 展示周历 + 标签 + 解释
    │
    ▼
[用户] 反馈（"宝宝吃了菠菜有反应"）
    │
    ▼
[对话记忆] 记录反馈 → 下次计划时影响排敏间隔计算
```

### 7.2 关键路径的确定性保证

```
步骤                    控制方式               LLM参与？
─────────────────────────────────────────────────────
阶段判断                age_rules 硬规则        ❌
过敏拦截                allergen_rules 硬规则    ❌
食材适龄筛选             age_rules 硬规则        ❌
配料表切分              LLM 辅助                ✅ (但需后验匹配)
配料成分匹配             ingredients 表查询       ❌
周计划约束排序           规则 + LLM 混合           ✅
营养缺口检测             nutrition_rules          ❌
计划二次验证             全部规则重新执行          ❌
解释生成                 LLM                     ✅ (纯语言任务)
```

## 8. 技术选型

### 8.1 选型总表

| 层级 | 技术 | 版本 | 理由 |
|------|------|------|------|
| 前端 | Streamlit | latest | 立项约定，快速出原型，Python 全家桶 |
| LLM API | 待定（可切换） | — | 抽象接口层，具体模型可换 |
| 规则引擎 | 纯 Python 函数 | — | 零依赖，确定性高 |
| 结构化数据 | JSON + SQLite | — | JSON 存静态知识，SQLite 存可变数据 |
| 数据清洗 | Pandas | ≥1.5 | 处理 USDA、Open Food Facts 等数据源 |
| HTTP 请求 | requests | — | 调用 Open Food Facts API |
| 向量检索（可选后期） | Chroma | latest | 如需 RAG 补充层 |

### 8.2 为什么不选某些技术

| 技术 | 不选的理由 |
|------|-----------|
| **知识图谱 (Neo4j/NetworkX)** | 时间线紧，JSON+SQLite + 规则函数等价满足查询需求，且确定性更强 |
| **向量数据库 (主存储)** | 安全规则不能靠"相似度"，需要精确命中 |
| **纯 LLM 驱动** | 与立项中的"安全判断由规则库完成"矛盾 |
| **RESTful 后端 (Flask/FastAPI)** | Streamlit 直接运行 Python，当前阶段不需要独立后端；后续如果拆分可加 |
| **Docker** | 团队不需要分布式部署，Streamlit 直接运行即可 |

### 8.3 LLM 的职责边界

```
LLM 做：
  ✓ 自然语言→结构化（宝宝画像抽取）
  ✓ 配料表文字切分
  ✓ 未收录成分的候选类别推断（需标注"未验证"）
  ✓ 相似/等计划排序中的灵活调节
  ✓ 生成自然语言解释
  ✓ 处理边缘/未覆盖情况

LLM 不做：
  ✗ 任何安全决策（是否过敏、是否适龄）
  ✗ 生成具体的营养数值
  ✗ 决定"能吃""不能吃"的标签
  ✗ 生成未经规则验证的食材建议
```

## 11. 关键算法说明

### 11.1 过敏原语义匹配（三级 fallback）

```
resolve_allergen_query("海鲜")
  │
  ├─ Level 1: umbrella_terms 精确匹配
  │   "海鲜" → ["鱼类", "虾"] → [allergen_004, allergen_009]  ✅
  │
  ├─ Level 2: 过敏原名/别名匹配
  │   "蛋" → 匹配鸡蛋别名 → [allergen_001]
  │
  └─ Level 3: LLM 语义解析
      Prompt 包含全部 9 种过敏原 ID + 别名清单
      只输出 JSON 数组，过滤只保留 KB 中存在的 ID
      如 "发物" → LLM → [allergen_004, allergen_009, allergen_001]
```

### 11.2 用户反馈闭环

```
家长在周计划页面标记食材反应
    ↓
FeedbackStore 持久化（JSON）
    ↓
下次生成计划时：
  ├─ moderate/severe 反应 → avoid（自动从候选池移除）
  ├─ mild 反应 → caution（降低优先级）
  └─ none → 放宽观察期
    ↓
check_cross_category_caution(): 同类食材联动提示
```

### 11.3 周计划生成算法

```
plan_foods = tried_pool + recommended_new[:5]
    ↓
_constraint_rank(): 铁含量加分 + 营养素覆盖排序
    ↓
_distribute_categories(): 类别轮转，避免同类连续
    ↓
_select_new_foods(): 新食材优先排周一/周二（留观察窗口）
    ↓
_generate_weekly_plan(): 7天逐日安排，类别不重复
```

## 附录：架构原则速查

```
1. 安全规则不能过 LLM → 必须硬编码
2. 知识来源必须可追溯 → 每个规则/数据点标注来源文件
3. 决策路径必须可解释 → 每个标签附带规则引用和原因
4. 渐进式复杂 → 先用规则跑通核心，LLM 只补灵活性
5. 数据与逻辑分离 → JSON/SQLite 管数据，Python 函数管逻辑
6. 校验冗余 → 计划生成后二次验证
7. LLM 只做 NLU → 配料切分、过敏原语义解析、解释生成
8. 用户反馈闭环 → 反应记录自动调整后续推荐
```
