一、场景与关键功能界定

1.1 场景说明

婴幼儿辅食添加期（6～12 月龄）是营养转换和安全风险并存的窗口期。家长既需要了解每个阶段适合引入何种食材，又必须规避过敏、窒息、高钠高糖等安全隐患。然而，市面上的辅食信息碎片化严重，商品配料表专业而难懂，家长常常面对「鸡蛋什么时候能加」「这个果泥袋含糖是否过多」「宝宝对牛奶过敏，配料里的乳清蛋白安全吗」等问题时缺乏可靠、可解释的即时指导。本项目面向这一场景，构建一个轻量、可运行的辅食推荐与过敏预警原型系统。

1.2 关键功能

本系统围绕以下五项关键功能展开：

（1）候选食物安全评估。输入宝宝月龄、过敏史等画像信息与一组候选食物（可为手工录入的食材或通过商品条码获取的辅食产品），系统对每个候选食物输出三级安全标签——适合（safe）、谨慎（caution）或避免（avoid），并附带风险原因与可追溯的科学来源。

（2）过敏原预警。系统内置 9 类常见食物过敏原的中英文别名及交叉反应血缘关系（例如牛奶→乳清蛋白/酪蛋白），在配料表和食材名称中执行多级匹配，并在不确定时通过大模型语义解析将家长的自然语言表述（如「海鲜」「蛋奶制品」）展开为具体过敏原。

（3）七日辅食计划生成。基于安全过滤后的食材池和宝宝的月龄阶段、已尝试食物、历史不良反应，生成一周逐日辅食安排，区分新食材与已知食材，控制新食物引入节奏，标注每餐的质地、做法建议和营养要点。

（4）商品配料表解读。支持拍照或手动输入配料表文本，解析其中的隐藏过敏原、添加糖和添加盐成分，以家长可理解的中文反馈风险项。

（5）自由对话问答。基于 TF-IDF 检索增强生成，从 28 份国内外婴幼儿喂养标准与指南中检索相关段落，结合大模型生成自然语言回答，并在涉及医疗建议时附加免责声明。

1.3 项目重心

本项目采用「原型重心」路线。核心目标是做出一个可运行、可演示的端到端原型，在真实输入（宝宝画像 + 候选食物 + 配料表）上验证规则增强 AI 系统的可行性与安全性边界，而非追求大模型的文本生成质量本身。

二、技术任务与方法选择——后端系统设计

2.1 总体架构

系统的技术架构自底向上分为四层。数据层以 JSON 文件存储静态领域知识（食材、过敏原、月龄阶段、营养素、食材类别等），以 SQLite 存储可变商品和配料数据，以本地 JSON 文件持久化用户反馈。计算层由规则引擎和智能体组成：规则引擎包含九个独立检测模块，对每份输入食材执行确定性安全评估；七个智能体分别负责安全边界判断、计划生成、用户画像提取、标签解析、对话问答、输出校验和自然语言表达。接口层通过 FastAPI 暴露 11 个 RESTful 端点，前端可选 Streamlit 原型界面或 React Web 单页应用。评测适配层通过独立的 eval_adapter 模块为苏冠辰维护的评测框架提供标准化调用入口。

该架构的核心设计原则是「安全不过大模型」：过敏拦截、月龄门槛、添加糖盐检测等高风险决策完全由确定性规则引擎执行，大模型仅用于自然语言理解、计划排序与多样性增强、自由对话等任务，且大模型生成的计划仍需经过规则引擎二次校验。

2.2 数据层：知识底座构建

静态知识以 JSON 编码，包含 40 种食材（其中 4 种标记为高铁食材、11 种标记为潜在过敏原）、9 类过敏原（含总计 60 余条中英文别名）、30 条伞状语义术语（支持从口语化表述映射到规范化过敏原 ID）、3 个月龄阶段（吞咽期 6～8 月、咀嚼期 9～11 月、过渡家庭饮食期 12 月+）、7 种关键营养素（铁、锌、钙、维生素 D、DHA、蛋白质、维生素 C）、11 个食材类别和 8 类食材替代关系。数据来源覆盖 CDC 婴儿喂养指南、WHO 补充喂养原则、中国食物成分表、USDA FoodData Central 和 Open Food Facts。

可变知识以 SQLite 表和本地 JSON 文件存储，包括商品条码对应关系、配料成分表、用户反馈记录（含食物名称、不良反应类型、严重程度和发生日期）。用户反馈模块提供 get_food_safety_label 接口，根据历史不良反应的严重程度自动将食物标记为「避免」「谨慎」或「适合」。

为兼顾可扩展性和确定性安全性，知识库后端设计为可切换架构：默认采用 JSON + SQLite 组合（零外部依赖、纯本地运行），同时提供了 Neo4j 图数据库实现（通过环境变量 KB_BACKEND=neo4j 启用），内置 Cypher 导入脚本，支持以图查询方式追溯食材→营养素的多对多关系以及商品→配料→过敏原的全路径。两种后端通过 Python Protocol 类型定义统一接口，上层代码无需感知后端差异。

2.3 规则引擎：九模块确定性安全评估

规则引擎是系统安全性的核心。RuleEngine.evaluate_food(food, profile) 方法对每份食材按固定顺序执行九项检查，逐项产生 tag（avoid / caution / suitable）、reason 和 source 标注，最终以所有检查中的最高警告级别作为食材的整体判定。九个检查模块及其判定逻辑如下：

（1）过敏原检测（rules/allergen.py）。读取宝宝画像中的已知过敏原列表，通过 allergens.json 的 aliases 字段执行子串不区分大小写匹配，并自动追溯 cross_reactive 血缘关系（例如牛奶过敏则乳清蛋白和酪蛋白也判为命中）。在 strict_mode 下，对低置信度匹配结果收敛为 caution 而非直接判 avoid。

（2）月龄门槛（rules/age.py）。检查食材的 min_age_months 是否大于宝宝当前月龄（或矫正月龄）。若宝宝不足 6 月龄，全部候选食材统一判 avoid；若食材最低推荐月龄未达到，判 caution；月龄差在 1 个月以内时，strict_mode 下收敛为 caution 而非 avoid，避免因边界误差误杀临近适龄食材。

（3）窒息风险分级（在 engine.py 中与月龄规则协同）。将食材的 choking_risk 字段与月龄组合判断：整颗或硬质食物在 12 月龄以下判 avoid，12 月龄以上判 caution；软质食物仅判 caution。

（4）质地匹配（rules/texture.py）。将食材的质地属性和月龄阶段的期待质地统一归一化到三个 canonical 等级（puree 泥糊状 / minced 碎末状 / chunky 小块），按等级数值比较：食材质地等级高于阶段等级则判为质地不匹配（caution），相等或低于则通过。该归一化是本项目开发过程中根据评测反馈实施的重要修复，此前因中英文质地标签不一致（食材以英文 "puree" 标注而阶段以中文 "泥糊状" 定义）导致所有食材被误判为质地不匹配。

（5）添加糖检测（rules/additive.py）。检测食材或配料表中是否含有 13 类常见添加糖关键词（如果糖糖浆、浓缩果汁等）：12 月龄以下判 avoid，12 月龄以上判 caution。

（6）添加盐与高钠检测（rules/additive.py）。检测含盐关键词及钠含量是否超标（每 100 克超过 200 毫克钠）：12 月龄以下判 avoid。

（7）排敏间隔检测（rules/interval.py）。对标记为「潜在过敏原」的新食材，检查距离上次引入同类过敏原食材的天数是否已达到 3 天观察期，不足则判 caution。

（8）营养素覆盖分析（rules/nutrition.py）。根据宝宝所处月龄阶段的关键营养素列表，检查当前食材池的总体覆盖情况，对缺失的关键营养素发出提醒。

（9）配料信息充足性检查（engine.py 1.8 节）。对通过外部包装接入的、配料文本为空或未知的食材，统一判 caution，避免因信息不足而将其当作安全食材纳入计划。

每条规则的判定均附带 source 字段，标注引用标准（如 WHO 补充喂养指南、CDC 婴儿喂养指南、Codex Stan 73 等），确保系统输出的安全判断可追溯、可审计。

2.4 外部食材包装器

评测用例中存在约三分之一来自系统知识库之外的候选食材。为保证这些食材也能获得规则引擎的完整评估，系统在 kb/external_food.py 中实现了外部食材包装器。resolve_food 函数作为统一入口：先以中英文名称分别在知识库中查询；未命中时，将候选食材的原生字段（contains_milk / is_choking_risk_candidate / contains_added_salt / sodium_mg_per_100g 等）包装为一个带 _external: True 标记的内部字典，使规则引擎逐项检查时能够读取到与内置食材等价的安全字段。该模块的核心原则是「不丢弃数据」，确保评测输入中的每一份安全信息都被充分利用。

2.5 智能体层：七智能体协作流程

智能体层继承自 BaseAgent 抽象基类，分为两类：LLMAgent 可调用大模型，RuleAgent 仅依赖规则引擎。系统包含七个智能体，各司其职：

（1）SafetyBoundaryAgent（安全边界智能体，继承 RuleAgent）。系统的安全守门人。按七步流程处理每次请求：判断月龄阶段→提取发育信号→全局月龄阻断（低于 6 月龄全部判 avoid）→逐食材调用规则引擎评估→直接过敏原匹配→大模型从备注文本提取隐藏过敏原→关键词规则兜底。输出包含逐食材安全标签、备注中识别的规避食材及发育准备判定。

（2）PlanGenerationAgent（计划生成智能体，继承 LLMAgent）。负责生成七日辅食计划。在规则模式下，执行约束排序（高铁食材优先、同类食材轮转分散）和新食物选择（每周最多 3 种，已尝试食材排除），随后生成七天逐日安排。在 LLM 模式下，将规则引擎过滤后的安全食材池与完整宝宝画像写入 prompt，由大模型完成排序、多样化和逐日安排，失败时自动回退到规则模式。评测路径中，LLM 模式通过 use_llm 参数启用。

（3）ValidationAgent（校验智能体，继承 RuleAgent）。纯规则引擎，不受大模型影响。在计划生成后对每一天的食材清单执行二次硬约束验证，若发现过敏冲突、月龄不匹配等问题则标记为拒绝。是 PlanGenerationAgent 的安全冗余层。

（4）UserProfileAgent（用户画像智能体，继承 LLMAgent）。从家长的自然语言输入中提取结构化宝宝画像（月龄、过敏原、喂养方式、已尝试食物等），对提取结果执行确定性范围校验（月龄限 0～36 个月，过敏原标准化为列表），并填充合理默认值。

（5）LabelParsingAgent（标签解析智能体，继承 LLMAgent）。解析配料表文本，输出成分风险标签。采用双级切分策略（大模型优先，正则 fallback），然后依次执行数据库成分匹配、过敏原别名匹配和添加糖关键词静态检测。

（6）ChatAgent（对话智能体，继承 LLMAgent）。处理自由对话问答，通过关键词和实体抽取自动调度四项内置工具（查食材、查过敏原、查适龄食材、评估食材），并使用 RAG 检索补充知识库中未直接覆盖的标准原文。

（7）DialogueAgent（对话记忆智能体，继承 LLMAgent）。系统内唯一不参与决策的智能体，仅负责将结构化系统输出（安全评估结果、周计划、校验反馈）转换为温暖、可理解的自然语言表达。

2.6 RAG 检索增强生成

在对话问答和开放文本回答场景中，系统通过 kb/rag.py 中的 RAGRetriever 进行检索增强。该模块从项目收集的 28 份国内外婴幼儿喂养标准与指南（PDF 和 Markdown 格式）中提取文本，以 500 字符为窗口、80 字符重叠进行切块，使用 scikit-learn 的 TfidfVectorizer 构建 4742 块文档的本地索引，序列化为 pickle 缓存文件。检索时计算查询与文档块的 cosine 相似度，返回 top-k 片段并附加来源标注，拼入大模型的上下文。该方案无需下载或部署任何嵌入模型，纯 CPU 运行，可在数秒内完成初始化。

2.7 评测适配器

为配合苏冠辰独立维护的评测框架，系统在 eval_adapter.py 中提供了五个标准化入口函数：evaluate_candidates（候选食物安全评估）、extract_profile（画像抽取）、generate_plan（周计划生成）、parse_label（配料表解析）和 chat（自由对话）。适配器通过 _ensure_init 懒初始化机制确保全局单例（知识库、大模型适配器、规则引擎、七个智能体、反馈存储）在首次调用时完成加载，后续调用零开销。该适配器还负责在评测模式下向规则引擎传递 strict_mode 参数、向计划生成智能体传递 use_llm 参数、并在计划输出中补全 avoid_food_ids 和规则触发原因列表。

三、实现过程——后端开发与迭代

3.1 开发环境与工具链

后端以 Python 3 实现，依赖管理使用 pip，虚拟环境为 Conda。知识底座以 JSON 编码静态数据、以 SQLite 存储可变数据，通过 Python 内置 json 和 sqlite3 模块访问。大模型通过 OpenAI 兼容 API 调用 DeepSeek-V4-Flash，由 llm/openai_adapter.py 统一封装。Web 服务基于 FastAPI 框架，以 uvicorn 运行在本地 8000 端口。代码版本控制使用 Git，仓库托管于 GitHub。测试覆盖采用自主编写的测试文件，涵盖 16 项管线测试和 20 项综合测试，共计 36 条用例在每次提交前全部通过。

3.2 开发阶段与关键节点

第一阶段（2026 年 5 月上旬）：知识底座搭建与规则引擎原型。完成了 40 种食材、9 类过敏原的知识整理与 JSON 编码；实现了 RuleEngine 的前六个检查模块（过敏原、月龄、质地、添加糖盐、营养素覆盖）；搭建了 FastAPI 基础路由和 Streamlit 原型界面。此阶段的核心挑战是知识体系统一性问题：不同来源（CDC、WHO、中国食物成分表）对同一营养素使用不同的单位或基准，需要逐一标准化。

第二阶段（5 月中旬）：智能体层与评测适配接入。实现了七个智能体的完整流程；构建了外部食材包装器使评测中的所有候选食材都能走通规则引擎；编写了 eval_adapter.py 作为评测框架的标准化入口。此阶段通过实际评测数据暴露了多项深层 bug：中英文质地标签不匹配导致全部食材误判质地不合规；规则 ID 映射使用子串匹配造成大量误触发；计划生成路径未读取用户反馈数据；外部食材的安全字段被丢弃等。

第三阶段（5 月下旬至 6 月上旬）：评测反馈驱动的迭代修复。这是开发过程中最关键、最密集的阶段。根据苏冠辰的评测输出，共识别并修复了五类系统性问题：（1）窒息风险从统一的 avoid 改为按月龄分级（12 月龄以下 avoid，以上 caution）；（2）质地匹配从直接字符串比较改为 canonical 三等级归一化，完全消除了中英文不一致带来的误判；（3）未知食材的规则 ID 映射从缺失补全到精确匹配（从子串「过敏」误触发泛化规则 ID 改为按具体过敏原关键词逐项匹配）；（4）计划生成模块新增 LLM 模式，让大模型基于安全食材池编排计划以解决规则模式下计划重复、缺乏多样性的问题；（5）中英文食物名统一检查，修复了已尝试食物列表中英文名不一致导致的错误标记问题。

每轮修复完成后均执行 36 项回归测试验证，并通过苏冠辰评测框架重跑评估。整个迭代过程共计 15 次代码提交，每轮迭代都直接响应评测数据中的具体问题。

3.3 关键技术决策

在开发过程中，以下决策对系统架构和最终表现产生了关键影响：

（1）知识表示选择 JSON+SQLite 而非知识图谱作为主后端。虽然 Neo4j 图数据库在食材替代关系查询和过敏原路径追踪方面更为自然，但考虑到项目时间线紧张（需在 6 月 10 日口头汇报前完成可演示原型）、JSON+SQLite 的迭代速度和确定性更强，最终采取了双后端可切换架构：日常开发和评测使用 JSON 后端，图查询演示时切换至 Neo4j。

（2）安全不过大模型的设计边界。在早期原型中，大模型被赋予更多决策权（直接判断食材是否安全），但测试中频繁出现边际条件不一致和遗漏过敏原的情况。后续明确划定大模型不可越过的安全决策红线：过敏拦截、月龄门槛、添加糖盐检测完全由规则引擎执行；大模型仅在语义理解（对话中提取过敏原、解析配料表）和表达多样性（计划排序、自然语言回答）中发挥作用。

（3）LLM 计划生成中「候选约束」策略。为避免大模型在计划中推荐安全池之外的食物（幻觉），prompt 明确要求仅从给定食材池中选择，并附完整列表。同时设置自动 fallback 机制：如果大模型调用失败或返回格式不合法，系统自动回退到确定性规则模式生成计划，保证服务不中断。

（4）评测适配器的「不丢弃数据」原则。面对评测数据中约三分之一的未知食材（不在内置知识库中），选择了包装而非丢弃的策略：将所有原始字段逐项映射为规则引擎可消费的内部格式，使得即使未收录的食材也能获得加糖、加盐、窒息风险、过敏原标记等完整评估。这个决策直接影响了候选食物选择任务的评测成绩——在早期版本中因 4 个字段被丢弃导致外部食材的覆盖率仅为 0.333。

从后端系统设计与实现的角度分析，评测结果揭示了两个核心洞察。第一，在候选食物安全分类和严重风险识别任务中，BabyBites 相较于纯大语言模型基线的显著优势（食物级 Accuracy 0.856 vs 0.701，严重风险召回率 0.993 vs 0.907）证实了显式规则和结构化知识库在安全边界判断中的决定性价值——这与系统的核心设计原则「安全不过大模型」吻合。规则引擎中的过敏原血缘扩展、月龄门槛阻断和窒息风险分级三项机制是贡献最大的安全冗余层。第二，在画像抽取和开放回答任务中，BabyBites 未展现出超越基线的能力，说明当前的后端实现在「将结构化的安全优势传递到非结构化的自然语言生成环节」这一路径上仍存在瓶颈。尽管系统的 ChatAgent 已具备工具调度、RAG 检索和候选食材注入能力，但检索到的标准原文如何在生成中被有效引用、如何平衡安全表达的准确性与语言的流畅性，仍是值得继续改进的方向。

从后端工程视角看，本系统最重要的启示在于：在安全敏感领域，AI 系统的价值往往不在于模型有多么复杂，而在于不确定性的边界是否被明确划定。九块确定性规则各自做的事情都很简单——字符串匹配、数值比较、阈值判断——但合在一起构成了一张细密的「不能做什么」的安全网。这张网的存在使得大模型可以在网内自由编排，而无需承担安全判断的负担。这种「确定性约束 + 生成式编排」的分层架构，或许可以推广到其他安全敏感的 AI 应用场景（如药物相互作用检查、电气安全审查等）。当然，它也有明确的边界：规则引擎只能执行被编码的检查，无法应对未被预见的风险类型；知识的规模和质量决定了系统的覆盖面——本系统的 40 种食材和 9 类过敏原远未穷尽真实世界的复杂性；评测中的标准答案本身基于预定义规则生成，不能等同于儿科或营养专家的逐例判断。
